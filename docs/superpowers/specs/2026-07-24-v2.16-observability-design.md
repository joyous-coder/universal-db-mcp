# Universal DB MCP — v2.16 Observability 设计文档

**日期**: 2026-07-24
**作者**: brainstorming 会话
**状态**: 待用户审阅
**范围**: v2.16 P3 主线 — 运维可观测性（连接池指标 + 查询统计 + 慢查询历史 + 健康检查 + 启动信息）

---

## 1. 背景与目标

v2.15 完成 P0/P1/P2 后，17 个数据库适配器全部支持连接池、`executeScript` / `executeBatch` / `generate_sample_data` 等 v2.15.0 引入的工具已上线，Trusted Publishing 配置完毕。

下一步主线选定为 **Observability 运维可观测性**：
- 解决生产环境连接池使用情况、查询延迟分布、慢查询定位**只能靠 log 肉眼扫**的痛点
- 让 SRE / DBA 能接 Prometheus / Grafana 标准生态
- 让 LLM（通过 MCP tool）能自助诊断"为什么这次查询慢"

**配套不做的（推到 v2.17+）**:
- Query Experience（Explain Plan / SQL Lint / 查询历史）— 留 v2.17
- Multi-DB 管理 — 留 v3.x
- Data Governance — 留 v3.x

**配套后续任务**:
- 跑通后写 `docs/observability.md`，含 Prometheus scrape config 示例 + Grafana dashboard JSON 模板

---

## 2. 非目标 (Non-goals)

- 不破坏现有 API 向后兼容（`/api/health` 字段只增不减，新端点独立）
- 不引入新依赖（手写 Prometheus text format，~250 行可控代码）
- 不重写 `ConnectionManager` / `BaseAdapter` 接口
- 不引入 OpenTelemetry（未来要加，OTel 是 sampler 模式不冲突，本 spec 不做）
- 不做远程 push gateway（Prometheus pull 已够用）
- 不做指标持久化（纯内存 + 环形 buffer）
- 不做 admin UI（属于 Grafana 职责）
- 不埋 Mongo / Redis / ClickHouse 的 pool 指标（非 pool 模式，简单计数即可）

## 3. 架构总览

核心思路：引入一个 `MetricsRegistry` 单例作为"埋点中心"，通过包装函数的形式插入到 13 个 pool-backed adapter 和 `DatabaseService` 的关键路径上。指标数据走 `Counter` / `Gauge` / `Histogram` / `RingBuffer` 4 种数据结构，HTTP `/metrics` 端点 emit Prometheus 文本格式，MCP `get_metrics` tool 返回 JSON。

```
┌─────────────────────────────────────────────────────────────┐
│                        客户端                                │
│  Claude Desktop (MCP)   /   Prometheus   /   LLM (MCP)       │
└──────────┬───────────────┬────────────────────┬──────────────┘
           │               │                    │
           │ MCP tool      │ GET /metrics       │ get_metrics
           │               │ (text/plain)       │ (json)
           ▼               ▼                    ▼
┌─────────────────────────────────────────────────────────────┐
│                  DatabaseService                            │
│  - query()  ──► MetricsRegistry.observeQuery()              │
│  - executeScript() ──► 同上                                │
│  - getSchema() ──► 同上                                   │
└──────────┬──────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────────┐
│  Pool Adapter (mysql/pg/oracle/...)  ──►  PoolMetrics        │
│  - acquire()  →  counter: db_pool_acquire_total{db}         │
│  - wait >10ms →  histogram: db_pool_acquire_seconds{db}     │
│  - timeout    →  counter: db_pool_timeout_total{db}         │
└─────────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────────┐
│  MetricsRegistry (src/utils/metrics.ts, ~250 行)             │
│  - Counter { name, help, labelValues: Map<string,number> }  │
│  - Gauge   { name, help, fn: () => number }                 │
│  - Histogram { name, help, buckets, counts: number[] }      │
│  - RingBuffer<T> { capacity, items: T[] }                   │
│  - format() → string (Prometheus text format)              │
│  - toJSON() → object (MCP tool 用)                          │
└─────────────────────────────────────────────────────────────┘
```

**关键决策**:
1. **Registry 是单例**（`export const metrics = new MetricsRegistry()`），任何地方都能 `import { metrics }` 直接埋点
2. **Gauge 用 lazy 拉取**（`fn: () => number`）而非事件驱动——避免对连接池做侵入式修改
3. **慢查询 RingBuffer 默认 100 条**（环形覆盖）
4. **不重写任何 adapter 的内部状态**——通过包装 connection acquire / release 拿指标

## 4. 核心组件 API

`src/utils/metrics.ts` 暴露 4 类数据结构 + 1 个 Registry：

```typescript
type Labels = Record<string, string>;

// 1. Counter：单调递增（如 acquire 次数、错误数）
export class Counter {
  inc(labels: Labels, n = 1): void;
  get(labels: Labels): number;          // 0 if missing
}

// 2. Gauge：当前值（用 callback 懒拉取）
export class Gauge {
  constructor(name: string, help: string, collect: () => Array<{ labels: Labels; value: number }>);
}

// 3. Histogram：耗时/大小分布
export class Histogram {
  constructor(name: string, help: string, buckets?: number[]); // 默认 [0.005,0.01,0.025,...,10]
  observe(labels: Labels, value: number): void;
}

// 4. RingBuffer<T>：固定容量、覆盖最旧
export class RingBuffer<T> {
  constructor(capacity: number);
  push(item: T): void;
  toArray(): readonly T[];              // 新到旧
  clear(): void;
}

// 主 Registry
export class MetricsRegistry {
  counter(name: string, help: string): Counter;
  gauge(name: string, help: string, collect: Gauge['collect']): Gauge;
  histogram(name: string, help: string, buckets?: number[]): Histogram;
  ringBuffer<T>(name: string, capacity: number): RingBuffer<T>;

  format(): string;                     // Prometheus 文本格式
  toJSON(): MetricsSnapshot;            // 给 MCP tool 用

  reset(): void;                        // 测试用
  isEnabled(): boolean;                 // 跟 DB_METRICS_ENABLED 联动
}

export const metrics = new MetricsRegistry();  // 全局单例
```

**关键设计点**:
- `Counter` 内部用 `Map<string /* labelHash */, number>` 存储——同名 counter 不同 label set 共享同一对象
- `format()` 严格遵循 Prometheus exposition format（`# HELP` / `# TYPE` / 指标行）
- `Histogram` 用 cumulative bucket（`le="0.005"` 包含 ≤ 5ms 的样本）— Prometheus 标准
- `RingBuffer` 用头尾指针实现，O(1) push
- Counter label set 上限 1000（LRU 淘汰），防恶意 label 爆炸

**典型用法**:
```typescript
import { metrics } from './utils/metrics.js';

const start = performance.now();
const conn = await pool.getConnection();
const dur = (performance.now() - start) / 1000;
metrics.histogram('db_pool_acquire_seconds', 'Pool acquire latency')
  .observe({ db: 'mysql' }, dur);
metrics.counter('db_pool_acquire_total', 'Total acquires').inc({ db: 'mysql' });
```

## 5. 集成点（埋点位置）

需要插入埋点的关键位置共 **5 类**，全在已有模块里，不新增抽象层：

| # | 位置 | 指标 | 实现方式 |
|---|------|------|---------|
| 1 | `PoolAdapter.withConnection()` / `withTransaction()` 公共包装 | `db_pool_acquire_total{db}` / `db_pool_acquire_seconds{db}` / `db_pool_timeout_total{db}` / `db_pool_active{db}` (gauge) | 包装函数首尾计时，13 个 pool-backed adapter 全部受益 |
| 2 | `DatabaseService.query()` / `executeBatch()` / `executeScript()` | `db_query_total{db,kind,status}` / `db_query_seconds{db,kind}` / `db_query_errors_total{db,kind,code}` | 包一层 try/finally 计时 + 错误码提取 |
| 3 | `DatabaseService.query()` 入口（query > `DB_SLOW_QUERY_THRESHOLD_MS`） | `db_slow_queries_total{db,kind}` + 推入 `RingBuffer<QueryEvent>` (capacity 100) | 复用现有 slow query 阈值逻辑 |
| 4 | `BaseAdapter.executeQuery()` 抛错时 | `db_query_errors_total` label `code` 提取 | 已有 `error.code`，无需新字段 |
| 5 | `DatabaseService` 启动时 | `db_info{db_type,version,permissions,uptime}` Gauge | `collect()` 返回单点 |

**为什么选这些点**:
- Pool wrapper 是观测连接池健康度（acquire 慢 = DB 负载高 / 网络问题）
- Query timing 给 LLM/用户看实际查询慢在哪
- 慢查询历史让 LLM 能自助诊断（"为什么这次查询慢"）
- 错误码分类（`TIMEOUT` / `AUTH_FAILED` / `CONN_LOST`）帮助区分"网络抖动"vs"真的写错 SQL"

**关键不动**:
- 不动 `ConnectionManager`（已经够复杂）
- 不动 `BaseAdapter` 接口（避免 17 个 adapter 全改）
- 不动 `safety.ts` / `sql-detector.ts`（它们没 IO 没耗时）
- 不埋 Mongo / Redis / ClickHouse 路径（非 pool 模式，简单计数即可）

**不埋的点**:
- Schema 缓存命中（已在内部计时，没必要 export）
- Template 解析（纯 CPU 操作 < 1ms）
- 鉴权 / 速率限制（属于 http 层，跟 DB observability 解耦）

## 6. 暴露面（HTTP + MCP）

### 6.1 HTTP 端点: `GET /metrics`

```
# HELP db_pool_acquire_total Total pool acquire attempts
# TYPE db_pool_acquire_total counter
db_pool_acquire_total{db="mysql",status="ok"} 142
db_pool_acquire_total{db="mysql",status="timeout"} 3

# HELP db_pool_acquire_seconds Pool acquire latency
# TYPE db_pool_acquire_seconds histogram
db_pool_acquire_seconds_bucket{db="mysql",le="0.005"} 80
db_pool_acquire_seconds_bucket{db="mysql",le="0.01"} 120
db_pool_acquire_seconds_bucket{db="mysql",le="+Inf"} 142
db_pool_acquire_seconds_count{db="mysql"} 142
db_pool_acquire_seconds_sum{db="mysql"} 1.234
```

- 路径: `/metrics`（Prometheus 标准，不放 `/api` 下）
- 鉴权: 默认匿名，env `DB_METRICS_IP_ALLOWLIST` 控制（逗号分隔 CIDR / 单 IP；默认 `0.0.0.0/0`）
- 状态码: 200 / 403（IP 拒绝）
- Content-Type: `text/plain; version=0.0.4; charset=utf-8`
- 实现: `src/http/routes/metrics.ts` (fastify route)
- 不计入速率限制（避免和 API_KEY 限流混在一起）

### 6.2 MCP tool: `get_metrics`

```json
// request
{ "name": "get_metrics", "arguments": { "category": "summary|slow_queries|all" } }

// response (summary)
{
  "uptime_seconds": 3600,
  "active_db": "mysql",
  "queries_total": 1234,
  "queries_errors": 5,
  "pool": {
    "mysql": { "acquire_total": 142, "acquire_timeout": 3, "active": 2 }
  },
  "latency_seconds": { "p50": 0.012, "p95": 0.087, "p99": 0.234 }
}

// response (slow_queries)
{
  "slow_queries": [
    { "ts": "2026-07-24T08:00:00Z", "db": "mysql", "kind": "select", "seconds": 5.2, "sql": "SELECT ...", "error": null }
  ]
}
```

- 实现: 加到 `src/mcp/tools/metrics.ts` 注册到 `DatabaseMCPServer`
- 权限: 不需要 `script` / `write`，纯 read-only（沿用现有 read 权限）
- Description: 控制 < 100 字符（避免吃 token 上下文）

### 6.3 `/api/health` 扩展（向后兼容）

```json
{
  "success": true,
  "data": {
    "status": "healthy",
    "uptime_seconds": 3600,
    "active_db": "mysql",
    "queries_total": 1234,
    "errors_total": 5
  }
}
```

老字段 `status` 保留，新增字段都是 optional，零破坏。

## 7. 配置与环境变量

新增 3 个环境变量，全部 optional，**默认值就是合理行为**：

| Env var | 默认 | 作用 | 行为 |
|---------|------|------|------|
| `DB_METRICS_ENABLED` | `true` | 全局开关 | `false` 时 Registry 一切操作 no-op，/metrics 返回空 body，MCP tool 报"metrics disabled" |
| `DB_METRICS_IP_ALLOWLIST` | (空，=全开) | /metrics 访问控制 | 逗号分隔 IP / CIDR。如 `10.0.0.0/8,192.168.1.5`；空 = 允许所有 |
| `DB_METRICS_SLOW_BUFFER_SIZE` | `100` | 慢查询环形 buffer 大小 | 0 = 不记录；> 0 = 容量 |

**集成到现有 config 体系**:
- `src/utils/config-loader.ts` 加 `metrics` section
- `AppConfig.metrics: { enabled, ipAllowList: string[], slowBufferSize: number }`
- HTTP server 启动时 read，CORS 路由 `/metrics` 用它做 IP 校验
- MCP server 启动时 read，`get_metrics` tool 看 `enabled` 决定是否报错

**现有 env 不动**:
- `DB_QUERY_TIMEOUT_MS`（已有）
- `DB_SLOW_QUERY_THRESHOLD_MS`（已有）— 复用，metrics 沿用同一个阈值

**配置加载顺序**（跟现有 env loader 一致）:
1. CLI 参数 (`--metrics-disabled` / `--metrics-allowlist x.x.x.x`)
2. 环境变量
3. `config/.mcp.json` 的 `metrics` 字段
4. 默认值

**配置校验**:
- `ipAllowList` 用 `node:net` 校验 CIDR 格式，错误时启动 warn 但不 fail
- `slowBufferSize` 必须是非负整数，错误时 warn 并用默认
- `DB_METRICS_ENABLED` 接受 `true/false/1/0/yes/no`（跟现有 `ALLOW_INSECURE_NO_AUTH` 一致）

## 8. 测试策略

### 8.1 单元测试 (新增 `tests/unit/metrics.test.ts`, ~150 行)
- `Counter` / `Gauge` / `Histogram` / `RingBuffer` 各自基础行为
- `MetricsRegistry.format()` 输出符合 Prometheus exposition format（用 regex 断言行格式）
- `MetricsRegistry.toJSON()` shape 稳定
- 跨 instance 共享 label set（同名 counter 不同 label 是不同 series）
- 内存无界增长保护：单 Counter 喂 2000 个不同 label set，验证 LRU 淘汰最旧 + warn 日志
- `isEnabled() = false` 时 inc/observe 全部 no-op（不修改内部 Map）

### 8.2 集成测试 (新增 `tests/integration/metrics-endpoint.test.ts`, ~80 行)
- HTTP `GET /metrics` 返回 200 + 正确 Content-Type
- `/metrics` body 含所有 4 类指标的 HELP/TYPE 行
- IP allowlist 拒绝：mock 不同 IP，验证 403
- 关闭 `DB_METRICS_ENABLED=false` 后 body 为空

### 8.3 MCP tool 测试 (新增 `tests/unit/mcp-metrics-tool.test.ts`, ~60 行)
- `get_metrics({category: 'summary'})` 返回结构
- `get_metrics({category: 'slow_queries'})` 含最近查询
- `DB_METRICS_ENABLED=false` 时返回 "disabled" 错误

### 8.4 实跑验证 (手工 / docs)
- 起一个 mysql 连接，强制 `SELECT SLEEP(0.5)` 触发慢查询
- curl `/metrics` 看 `db_slow_queries_total` 增加
- 在 MCP 客户端调 `get_metrics({category: 'slow_queries'})` 看到刚跑的 SQL

### 8.5 基准 (可选, 加在 `docs/observability.md`)
- 关闭 metrics: 0% 开销（counter.inc() 走 no-op 分支）
- 开启 metrics, 无查询: < 0.1MB 内存, < 1% CPU
- 开启 metrics, 100 QPS: < 1MB 内存, < 2% CPU（counter hash table + ring buffer push）

- 现有 224 测试必须全过（重点：withConnection / withTransaction 行为不变）
- v2.15.2 修过的 pool 事务语义不能因为加埋点而退化

## 9. 风险与权衡

| 风险 | 等级 | 缓解 |
|------|------|------|
| Counter label 集合无界增长（恶意 LLM 喂随机 db 名） | 中 | 加 LRU 兜底：单 counter 最多 1000 个不同 label set，超过 LRU 淘汰 + 启动时 warn |
| Histogram bucket 选择不当导致精度差 | 低 | 用 Prometheus 标准 default buckets (`[0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10]`)，覆盖 5ms-10s 区间 |
| `/metrics` 被恶意抓取（暴露 DB 信息） | 低 | 现有 API_KEY 控制写入；/metrics 只读无副作用；可配 IP allowlist |
| 加埋点影响 hot path 性能 | 低 | counter.inc() 是 `Map.set`，实测 < 1μs；histogram.observe() 是 array increment < 1μs；不开时走 no-op |
| RingBuffer 序列化大 SQL 撑爆内存 | 中 | 单条 QueryEvent 限制 4KB（截断超长 SQL 末尾加 `/* truncated */`） |
| MCP tool description 吃 token | 低 | 描述控制在 < 100 字符，引用 doc 不展开 |
| Prometheus 抓取频率高时 lock 竞争 | 极低 | 全局单例 + 不可变 snapshot：format() 时浅拷贝 label map，调用方无锁读 |
| `DB_METRICS_ENABLED=false` 时 hot path 不能完全零开销 | 低 | 用 `if (metrics.isEnabled())` 在 wrapper 顶部短路，0 开销 |
| 17 个 adapter 行为差异导致埋点不准 | 中 | 只在公共 wrapper（`PoolAdapter.withConnection` / `DatabaseService.query`）埋，不动各 adapter 内部，行为统一 |
| 跟 OpenTelemetry 冲突 | 极低 | 未来如果要加 OTel，OTel 是 sampler / exporter 模式，不冲突；本 spec 不引入 OTel |

**未做（YAGNI）**:
- 远程 push gateway（Prometheus pull 已够用）
- 指标持久化（按澄清结果，纯内存 + 环形 buffer）
- 自定义 alert rule（属于上层告警系统职责）
- traceId 关联（无 OpenTelemetry）
- per-SQL 指纹归类（慢查询 SQL 多样，按 SQL 文本原样记录）
- admin UI dashboard（属于 Grafana 职责）
- multi-process 指标聚合（单进程单 Registry，未来分布式再说）

**回退方案**:
- 全局开关 `DB_METRICS_ENABLED=false` 一键全关
- `format()` / `toJSON()` 是纯函数，不依赖外部状态
- MetricsRegistry.reset() 测试时清零
- 不引入新依赖，0 迁移成本
